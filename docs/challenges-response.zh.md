# Botashka — 对设计挑战的回应

这是对 `challenges.md` 中对抗性评审的直接逐点回应。本文从一位已交付过生产系统（而非精心打磨的演示）的经验丰富的 Clojure 实践者的视角写就。

该评审诚实且有价值。其中有些是正确的。但很大一部分是用多租户、生产级平台的标准来衡量 Botashka，然后将由此产生的差距称为设计缺陷。这一框架错误贯穿了几乎每个章节。

---

## 关于总体评价

> "伪装成 agent 的脆弱代码执行器"

所有 agent 都是代码执行器。问题在于这个抽象是否带来了价值——对于一个本地的、单开发者的 Clojure 工具而言，它确实带来了价值。评审将"没有沙箱"和"没有版本控制"视为绝对失败。它们是有意识地做出的 v1 权衡。评审者知道这一点，仍然标记出来——这没问题，这就是评审的工作。但称之为"伪装"暗示了欺骗。这里没有欺骗。设计文档明确说明了这是什么。

---

## 1. 基本概念弱点

### "仅追加的 trace 作为唯一事实来源是错误的。真实状态是可变文件系统。"

部分正确。trace 是 *agent 决策* 的审计跟踪，而不是世界状态的快照。每个有史以来构建的数据库都有相同的属性：日志不包含行，它包含产生这些行的操作。trace 是你进行重放、调试和上下文组装所需要的——而不是文件系统镜像。"这是一个虚假的设计承诺"的说法误读了 trace 的用途。

### "子进程边界破坏了设计的状态流。`*result*` 无法在 `bb -f` 中存活。"

这是评审中最有力的观点，并且已经在规范中标记出来。挑战文件重复了它——公平。当前设计承认 `*result*` 是简单线性计划的便利设施，真正的跨任务组合需要显式的数据传递（文件、EDN、返回值）。这并不隐蔽。一个更完整的解决方案——跨工具调用保持状态的持久化 Babashka 进程——是自然的 v2 方向，v1 中没有任何东西阻止这一点。

### "通过 SCI 实现的 CodeAct 使用无沙箱的 eval，使执行正确性完全依赖 LLM 输出。"

是的。Claude Code 也是如此。每个执行代码的 agent 都是如此。问题在于信任模型是否对此诚实。Botashka 是一个由其作者运行的本地工具。操作者和用户是同一个人。将开发者自己的笔记本电脑与他们自己隔离是另一种剧场。

### "单一 `emit!` 将异质关注点过度集中。"

`emit!` 按 `:type` 分派——它不是无类型的。计划日志（`{:type :think}`）、工具输出（`{:type :observe}`）和 UI 事件（`{:type :ask}`）是不同的事件形状，只是通过同一个函数路由。这正是重点所在：一个传输缝合，多种事件类型。每个事件驱动的系统都是这样工作的。"这保证了隐式契约"的说法与具有必需 `:type` 字段的结构化事件 map 所提供的恰恰相反。

---

## 2. "简洁"主张中的虚假节约

### "正则验证是表演性的安全措施。"

同意。对 `s/def`/`s/fdef` 使用 `re-find` 是一个健全性检查，而不是安全门控。它捕获的是 LLM 生成 Python、shell 脚本或裸表达式而非带有 spec 的 Clojure 的情况。这就是它的工作。没有人声称它能防止恶意代码——设计明确表示，内置工具确认和人工审批门控才是高风险操作的实际安全机制。评审将"验证"（这看起来是正确的工件类型吗？）与"沙箱"（这会造成伤害吗？）混为一谈。这是不同的关注点。

### "手动 `git commit` 作为提升门槛，将质量完全外包给人工。"

对于本地工具而言，`git commit` 是正确的门控，因为开发者已经在这个循环中了。提交一个工具意味着它值得保留——这不是 CI，而是等同于保存一个你已经测试过并发现有用的脚本。在 v2 中添加自动化测试门控是个好主意，但将其缺失称为 v1 的失败忽略了上下文。开发者就是测试套件。

### "在 `plan-amend!` 上重写 `bb.edn` 制造了两个相互冲突的真相。"

设计是明确的：trace 具有权威性，`bb.edn` 仅用于显示。在 `plan-amend!` 上重写 `bb.edn` 是正确的，因为人类查看的窗口应该显示当前计划，而不是被放弃的那个。没有冲突——trace 包含完整的修订历史，包括带有 `:old-tasks` 和 `:new-tasks` 的 `:plan-amend` 事件。`bb.edn` 反映当前计划。它们服务于不同的读者。

### "EDN-on-CLI 在嵌套 map、包含换行符的字符串或二进制数据时会失败。"

对于复杂载荷而言是个有效关注点。Clojure 中的标准修复方法众所周知：将参数写入临时文件并传递路径。当这成为问题时，这是执行器中的一行代码更改。这不是架构问题——它是一个实现细节，推迟到真实案例出现时再处理。

---

## 3. LLM 可靠性问题

### "每条关键路径都假设 EDN 格式良好。"

每个 LLM 集成系统都如此。缓解措施很简单：`clojure.edn/read-string` 包装在 `try/catch` 中，加上一个将原始响应连同显式解析错误一起发回给 LLM 的重试路径。这是两个函数。设计不规定每个错误处理器，因为在看到真实失败模式之前规定错误处理器是过早优化。

### "GENERATE 验证将代码运行作为验证方式。"

在没有文件系统访问、网络访问或有副作用命名空间的隔离上下文中使用 `sci/eval-string`，与在生产中运行代码不同。SCI 的沙箱模型正是如此：在受限上下文中加载代码以检查其是否能解析和求值，只能访问声明的命名空间。评审者知道这一点，仍然将两者等同。这种描述是不公平的。

### "故障处理是递归式 LLM 驱动的。"

评审关于 `plan-amend!` 不应该是第一个恢复步骤的观点是正确的。规范说 `core.clj` 在 `react-step!` 返回 `{:status :error}` 时调用 `plan-amend!`——但预期的设计在 `react-step!` 内部首先有一个带反馈的重试循环（生成失败最多 3 次尝试）。规范可以更明确地说明升级阶梯：重试 → 带上下文重试 → `plan-amend!` → 询问人类。这是规范缺口，而非架构缺陷。

### "组合性决策要求 LLM 从被截断、不断漂移的 `tool-index.edn` 中回忆工具能力。"

工具索引在每次 `:think` 调用时从磁盘新鲜读取。它在会话中不会漂移。跨会话的过时索引随着库增长是一个真实问题——这是第 6 节中的可扩展性关注点，是一个有效的长期问题。对于 v1 中少量工具的情况，这不是实际问题。

## 4. 安全剧场

### "`re-find` 对 `s/def`/`s/fdef` 的检查，通过在前面加一个虚假 spec 同时嵌入任意破坏性副作用即可绕过。"

是的。Claude Code 也可以编写一个清空你磁盘的 bash 脚本。任何文本编辑器也可以。安全模型是：这是一个由开发者为开发者运行的本地工具，对最高风险的内置操作（`:shell`、`:llm-complete`）有确认门控。规范没有声称其他内容。称之为"安全剧场"意味着设计在假装安全。它并没有——它明确表示人类是最后的门控。

### "`:confirm true` 毫无意义，因为是同一个 agent 来决定是否设置该标志。"

`:confirm true` 由注册表设置，而不是由 LLM 设置。LLM 从 `tool-index.edn` 中选择 `:shell` 或 `:llm-complete`；`:confirm true` 标志由开发者烘焙到索引中。agent 无法决定不要求 `:shell` 的确认——当执行器从索引中读取到 `:confirm true` 时，会无条件地强制执行它。评审者误读了设计。

### "`git commit` 作为人工门控是建议性的，而非机械性的。"

正确。它本来就是建议性的。工具提升是人类编辑决策，而非自动化策略。设计不承诺机械性的强制执行。

---

## 5. 函数式编程纪律的幻觉

### "`llm-context` 是纯函数是营销说辞。它读取可变文件。"

`llm-context` 接受 `session-trace` 和 `event-type` 并返回一个 map。它不读取文件——它读取 trace。`tool-index` 由调用者传入（注入）。`:think` 路径中唯一的可变读取是从磁盘读取 `tool-index`，这发生在调用者调用 `llm-context` 之前。该函数本身是纯的。评审者将调用点与函数本身混为一谈。

### "仅追加的 trace 被截断和运行结束时的持久化所破坏。"

渲染时的截断不修改 trace。atom 是不变的。trace 本身是完全仅追加的。发送给 LLM 的是一个截断的视图——这是一个读操作，而非修改操作。这就是每个上下文窗口的工作方式：数据存在；视图受到约束。"崩溃时消失"的观点是有效的，在第 7 节中有所讨论。

### "工具库没有版本固定。"

真的。工具版本就是 git 提交。trace 不记录运行工具的提交 SHA——这对于可重现性来说是一个合理的缺口。实践中，对于本地开发者工具，你知道你提交了什么代码。对于生产可重现性，这需要加以解决。对 v2 而言是公平的批评。

---

## 6. 可扩展性与增长假设

### "在 8k/4k 处截断保证了重要早期上下文的丢失。"

所有 LLM 系统都有上下文窗口。所有系统都会截断。有趣的问题是截断策略：最旧优先、任务作用域、摘要压缩。Botashka v1 在最旧的 `:file-context` 和 `:observe` 事件处截断。这是正确的起点：大载荷先消失。更智能的窗口策略是自然的 v2 改进。将截断的存在称为设计失败，同样适用于有史以来构建的每个 agent 系统。

### "`tool-index.edn` 随着库增长会变得过时和嘈杂。"

有效的长期关注点。解决方案空间是众所周知的：语义搜索、能力聚类、废弃策略。这些是 v2+ 特性。对于 v1 中少量工具的情况，LLM 可以读取整个索引。

### "每个 `bb -f` 子进程排除了超时、取消或并行性。"

超时：`bb -f` 可以用 `timeout`（POSIX）或带 `:timeout` 的 Babashka 进程 API 包装。取消：进程有 PID，可以被杀死。并行性：对任务使用 `pmap`。这些都不需要架构重新设计。需要时只需几行代码。

### "没有长时间运行或后台任务的模型。"

公平。设计是同步的。带有异步工具结果的事件循环是一个重要扩展。对于声明的 v1 范围——单开发者、本地、顺序任务——这属于 v2 或 v3 的范畴。

---

## 7. 规范与现实之间的差距

### "`*result*` 无法在 `bb -f` 中存活。组合退化为文件系统传递。"

上面已经讨论过。文件系统传递是一种完全有效的组合机制，也是大多数 Unix 管道的工作方式。缺口是真实的；暗示它无法修复则不是。

### "`命令行上的 EDN 参数`将间歇性失败。"

见第 2 节。将复杂参数写入临时文件并传递路径。这是一个已知模式，修复起来微不足道。

### "`在会话结束时持久化 trace`与仅追加的持久性相矛盾。"

仅追加属性关于内存中的 atom——你永远不删除事件。在会话结束时持久化是一次写入；最后一个事件和写入之间的崩溃会丢失会话。修复方法是在每个事件上增量追加到 EDN 文件——而不是在会话结束时。这是对 `append-event!` 进行追加模式 `spit` 的一行代码更改。v1 中值得实现。

**这是评审中唯一一个应该在编写第一行实现代码之前解决的可操作事项。**

### "经过两次重新规划后，`bb.edn` 将不再连贯。"

两次重新规划后的 `bb.edn` 将显示当前计划。trace 将显示所有三个计划以及每个计划被替换的原因。对于阅读 `bb.edn` 的人来说，看到当前计划是正确行为。对于试图理解完整历史的人来说，trace 是正确的查阅之处。这些工具各司其职。

### "通过 `git commit` 进行工具提升在时间上与执行解耦。"

真的。在 `:execute` trace 事件中记录每个工具的提交 SHA 将弥补这一差距。这是一个小的补充。评审者说得对，这是缺失的。

## 8. 竞争现实检验

### "没有类型化的工具接口或 schema 验证的参数。"

Clojure.spec 提供了 schema 验证。它不是 JSON Schema，但表达能力更强。生成的工具验证自己的输入。弱点在于，当参数作为 EDN 字符串跨越子进程边界时，在边界处会失去这种验证——这由临时文件模式解决。这是一个真实的缺口，但不是根本性的缺口。

### "没有沙箱、能力作用域、超时或资源限制。"

对于运行开发者自己代码的本地开发者工具，OS 级沙箱提供的隔离与任何正常进程上的 seccomp 完全相同。工具以开发者的用户身份运行。这与 Makefile 或 shell 脚本的信任模型相同。Botashka 不是多租户平台。

### "没有结构化的可观测性。"

session trace 就是结构化的可观测性。每个事件都有一个 `:type` 和任务作用域的键。它是 EDN 而不是 JSON，但它是机器可读的、可查询的、完整的（除了崩溃持久化缺口之外）。评审将"不是 OpenTelemetry"等同于"没有可观测性"。这对于本地 v1 工具来说不是一个公平的标准。

## 证伪测试——接受

`challenges.md` 中的 7 个证伪测试是正确的，应该是 v1 工作后编写的第一批集成测试。具体而言：

| 测试 | 当前状态 |
|---|---|
| 生成带 `s/def` 加破坏性 I/O 的工具 | 已知缺口。通过高风险内置操作的 `:confirm true` 缓解。对于生成的工具未完全解决。 |
| 规划器发出格式错误的 EDN | 需要在 `core.clj` 中添加显式 `try/catch` + 重试。添加起来微不足道。 |
| 无限循环工具 | 需要在执行器中添加 `timeout` 包装器。添加起来微不足道。 |
| 更改已提升工具破坏会话 | 需要在 `:execute` 事件中记录提交 SHA。小的补充。 |
| 执行中途杀死进程 | 需要增量 trace 持久化。**应该在 v1 中修复。** |
| 会话超过截断限制 | 已知。截断策略对 v1 足够；在 v2 中改进。 |
| 将大型/嵌套 EDN 作为 CLI 参数 | 当参数超过阈值时，需要执行器中的临时文件回退。小的补充。 |

## 评审正确之处

- `*result*` 跨 `bb -f` 对于主要组合路径在架构上是有缺陷的。修复：持久化进程或显式文件传递。
- Trace 持久化应该是增量的，而不是在会话结束时。修复：一行代码更改，在 v1 中实现。
- `re-find` 验证不是安全门控。规范中应该明确声明这一点。
- 工具提交 SHA 应该在执行时记录以保证可重现性。小的补充。
- 升级阶梯（重试 → 带上下文重试 → `plan-amend!` → 询问人类）应该在规范中明确说明。

## 评审错误之处

- 将生产多租户标准应用于本地 v1 开发者工具。
- 称 `emit!` 为"无类型"——它在结构化事件 map 上分派。
- 声称 `llm-context` 读取可变文件——它将输入作为参数接受。
- 将隔离上下文中的 `sci/eval-string` 等同于生产执行。
- 将 `:confirm true` 标志视为 agent 可设置的——它是开发者控制的注册表元数据。
- 使用"脆弱"和"剧场"这样的框架，暗示欺骗而非权衡。

---

## 总体评估

Botashka v1 对于其本质而言是一个正确且诚实的设计：一个基于 Babashka、采用代码即行动模型的本地单开发者智能助手。它推迟的复杂性——沙箱、版本控制、并行性、崩溃安全持久化——恰恰是在 v1 中不重要、而在 v2 中极为重要的复杂性。评审的价值在于清晰地识别了 v2 工作清单。其弱点在于将该清单视为 v1 已损坏的证据。

在编写第一行实现代码之前值得修复的两项：

1. **增量 trace 持久化** — 在每次 `append-event!` 时追加到磁盘，而不是在会话结束时。
2. **规范中的显式重试升级阶梯** — 重试 → 带上下文重试 → `plan-amend!` → 询问人类。

其他一切要么是 v2 的关注点，要么是对设计的误读。

## Round 2 — 对反驳评分卡的回应

评审者带着一份对我反驳的评分评估回来了。这是他们写过的最有价值的内容。我将逐点回应。

---

### 关于元论证

> "元论证并不能覆盖所有情况。这些项目是 v1 的前提条件，而不是 v2 的可选改进。"

第 1 和第 2 项——我已经接受了。关于第 3 项（具体的超时/取消机制）："用 `timeout` 包装"确实未加规范，评审者将其标记出来是正确的。我会将其加入实现前修复清单。

---

### 关于反驳评分——我接受的修正

**`sci/eval-string` — "部分成立"：**

> "仅当命名空间被列入白名单且 FS/网络访问被真正排除时才成立。按照当前规范（'无能力限制'），eval 仍然可以消耗无限 CPU 和时间。"

这是评分卡中最尖锐的修正，也是正确的。规范称"隔离的 SCI 上下文"，但从未规定哪些命名空间被列入白名单。这使得安全声明变得空洞——SCI 可以被严格沙箱化，但前提是你要做这项工作。评审者在修复清单中添加的第三项是正确的：

> **SCI 命名空间白名单** — 明确声明在验证上下文中可访问哪些命名空间；验证不可能进行 FS/网络访问；添加超时。

这应加入实现前清单。这不是 v2 的关注点——它是让"隔离 SCI 上下文"真正有意义的东西。

**截断 — "部分成立——偏向合理化"：**

> "设计问题在于*截断策略*（什么被固定、什么被摘要、什么被丢弃）。'所有人都会截断'并不能解决朴素的最旧优先 FIFO 丢失导致的质量回退问题。"

公平。"所有人都会截断"是错误的论证。正确的论证是：对于会话较短、任务数量有限的 v1 工具，对最大载荷（`:file-context` 和 `:observe`）进行 FIFO 截断是足够的。问题是真实存在的——但评审者说得对，*策略*是未规范的，而不仅仅是机制。规范应该明确说明截断策略：大载荷优先截断；`:plan`、`:think` 和 `:plan-amend` 事件无论大小始终包含在内。

**无沙箱 eval — "部分成立——偏向合理化"：**

> "'他们也这么做'是合理化。最小防护措施（diff、cwd 围栏）可以在不违背本地工具前提的情况下减少误操作。"

接受。"他们也这么做"的论证是懒惰的。正确的论证是单操作者信任模型，而非先例。评审者的建议——diff 和 cwd 围栏——确实成本低廉，值得加入执行器。一个写入项目目录之外的生成工具几乎必然是个 bug，而 cwd 围栏只需一行代码。

---

### 关于 3 个真正开放的挑战

**1. 上下文管理策略**

> "朴素截断会主动损害主 agent 循环的质量——这是 v1 的正确性问题，而非可扩展性问题。"

我之前反驳得过于强硬。评审者说得对，策略对正确性很重要，而不仅仅是可扩展性。v1 的修复很简单，应该明确说明：`:plan`、`:think`、`:plan-amend` 和 `:user-input` 事件被固定——始终包含在内。仅当上下文压力较高时才截断或丢弃 `:file-context` 和 `:observe` 载荷。这使截断策略变得明确，并防止 agent 丢失其计划或决策历史。

**2. 不可逆操作的防护措施（超出 `:confirm true` 之外）**

> "生成的工具可以写入文件、发起网络调用、修改状态——而这些都不经过确认门控。人类看到的只是工具名称和参数，而不是工具实际会执行什么。"

这是最棘手的开放挑战，评审者说得对，我的反驳没有充分回应它。我说"人类是最后的门控"——但如果人类只能看到工具名称和参数，门控提供的保护是薄弱的。三个适合 v1 的具体缓解措施：

- 在首次执行前向人类展示生成工具的描述注释和 spec（而不仅仅是工具名称）。
- 执行器中的 cwd 围栏拒绝任何向项目目录之外写文件的操作，除非有明确的覆盖。
- `:confirm true` 应覆盖任何在其命名空间 requires 中包含 `http`、`io`、`shell` 或 `fs` 的生成工具。

这些都不是完整的沙箱化。它们在不需要容器的情况下缩小了影响范围。

**3. 健壮的进程监控**

> "清理工具内部产生的孙子进程，当工具在多个流上产生输出时的确定性日志汇聚，以及当 stdout 数据量大时的背压处理。"

承认这是真正开放的问题。v1 的做法：子进程上的超时处理挂起情况；stdout 在 4k 限制处被捕获并截断。孙子进程清理和流多路复用是 v2 的关注点，等到真实工具复杂度使其不可回避时再处理。评审者说得对，"PID 和 `timeout`"的回答过于草率——我会将其保留在开放清单中。

### 更新后的实现前修复清单

| # | 项目 | 优先级 |
|---|---|---|
| 1 | **增量 trace 持久化** — 在每次 `append-event!` 时原子性追加，而不是在会话结束时 | V1 阻塞项 |
| 2 | **显式重试升级阶梯** — 重试 → 带上下文重试 → `plan-amend!` → 询问人类，每级有有界尝试次数 | V1 阻塞项 |
| 3 | **SCI 命名空间白名单** — 声明验证上下文中可访问的命名空间；排除 FS/网络；添加执行超时 | V1 阻塞项 |
| 4 | **截断策略中的固定事件类型** — `:plan`、`:think`、`:plan-amend`、`:user-input` 始终包含；仅截断大载荷 | V1 正确性 |
| 5 | **执行器中的 cwd 围栏** — 拒绝生成工具向项目目录之外写文件 | V1 安全性 |
| 6 | **首次执行前展示工具描述** — 人类看到描述 + spec 输入/输出，而不仅仅是工具名称 | V1 安全性 |
| 7 | **子进程超时** — 可配置，由执行器强制执行，默认 30 秒 | V1 可靠性 |

第 1–3 项是阻塞项。第 4–7 项足够小，可以与第一批可运行代码一起实现。

### 最终评分

评审者的评分卡是诚实且论证充分的。它所指出的三个开放挑战确实是开放的——我在第一次回应中没有充分回应不可逆操作防护措施或 SCI 白名单问题。上下文管理策略的批评也比我之前承认的更为正确。

元论证（"v1 工具，而非平台"）对于结构性批评仍然成立。但评审者正确地识别出了我将其用作盾牌来掩护那些实际上廉价可修复的事项的地方。这些事项应该被修复。

其他一切要么是 v2 的关注点，要么是对设计的误读。
