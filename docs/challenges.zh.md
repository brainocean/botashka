# Botashka — 设计挑战与已知弱点

本文档记录了对当前设计最为严苛的诚实批评，这些批评来自对抗性设计评审。这些问题尚未解决——它们是必须在实现之前或实现过程中正面应对的开放性挑战。

---

## 总体评价

这是一个**伪装成 agent 的脆弱代码执行器。** 它在没有沙箱隔离、没有隔离机制、没有可重现性保障的情况下执行由 LLM 生成的代码，且验证流于表面。所谓"简洁"的设计选择——单一 `emit!`、EDN-over-CLI、仅追加的 trace、手动 `git commit` 提升——并没有消除复杂性，只是将复杂性推迟到了故障处理、安全性和可维护性上。

---

## 1. 基本概念弱点

- **通过 SCI 实现的 CodeAct 使用无沙箱的 eval**，使得执行的正确性和安全性完全依赖 LLM 的输出。"计划"与"执行"之间没有原则性的边界。
- **"仅追加的 trace 作为唯一事实来源"是错误的。** 真实状态是被任意工具修改的可变文件系统和网络。trace 无法重建世界状态——它记录的是意图和 stdout，而非实际效果。
- **子进程边界破坏了设计的状态流。** `*result*` 无法在 `bb -f` 中存活。任务之间只能通过带外 I/O 进行组合，这与 THINK/GENERATE/EXECUTE 循环隐含的数据流模型直接矛盾。
- **单一 `emit!` 将异质关注点过度集中**——计划日志、工具输出、UI 事件——汇入一个无类型的汇聚点。这保证了隐式契约和紧耦合，而非设计所声称的干净传输缝合。

---

## 2. "简洁"主张中的虚假节约

- **正则验证是表演性的安全措施。** 对 `s/def`/`s/fdef` 使用 `re-find` 加上 `sci/eval-string`，只是在任意代码运行后将复杂性转移到事后损害控制中——它并不能防止损害。
- **手动 `git commit` 作为提升门槛，将质量完全外包给人工。** 没有测试、没有版本控制、没有废弃路径——任何引用了已变更工具的现有计划都会悄无声息地崩溃。
- **在 `plan-amend!` 上重写 `bb.edn` 制造了两个相互冲突的"事实"。** 仅追加的 trace 是不可变的；`bb.edn` 是可变的。设计声称 trace 具有权威性，却允许 `bb.edn` 在无声中与其偏离。
- **EDN-on-CLI 传递参数虽然避免了 IPC 复杂性，但重新引入了引号限制、操作系统差异和载荷大小约束**，在面对任何实际工具输入时都会以非病理性方式失败——嵌套 map、包含换行符的字符串、二进制数据。

---

## 3. LLM 可靠性问题

- **每条关键路径都假设 EDN 格式良好。** 规划器输出、THINK 决策、工具参数、生成的源码——一个格式错误的 token 就会使循环停滞或破坏 trace。没有确定性的解析错误恢复路径。
- **GENERATE"验证"将代码运行作为验证方式。** 语法正确但逻辑错误或恶意的工具在构造上就能通过验证。验证和执行是同一个操作，只是换了个说法。
- **故障处理是递归式 LLM 驱动的。** `plan-amend!` 在失败时要求同一个失败的模型生成更好的计划。糟糕的模型响应会产生没有确定性出口的失败循环。
- **组合性决策要求 LLM 从被截断、不断漂移的 `tool-index.edn` 中回忆工具能力。** 在过时的索引上将 `:reuse` 和 `:generate` 错误分类，会悄无声息地降低每次执行的质量。

---

## 4. 安全剧场

- **`re-find` 对 `s/def`/`s/fdef` 的检查极易被绕过**，只需在前面加一个虚假的 spec，同时嵌入任意破坏性副作用。它提供的实际保护几乎为零，还会制造虚假的安全感。
- **`sci/eval-string` 没有沙箱、没有能力限制、没有超时，等同于"执行任意本地代码"。** 设计承认了这一缺口，却没有任何处理措施。
- **`:confirm true` 毫无意义**，因为是同一个编写代码的 agent 来决定是否设置该标志。人工门控是可选的，系统中没有任何东西强制执行它。
- **`git commit` 作为人工门控，系统中没有任何部分强制执行。** 工具可以在提交之前被使用。"提升"步骤是建议性的，而非机械性的。
- **nREPL V2 将 `println` 路由到 `:out` 的作用域不能约束行为。** 它只改变文本的去向，无法阻止数据泄露、文件系统写入或破坏性 I/O。

---

## 5. 函数式编程纪律的幻觉

- **"`llm-context` 是纯函数"是一种营销说辞。** 它在调用时依赖可变文件（`tool-index.edn`、`tools/*.clj`、`bb.edn`）。结果不具备引用透明性，在同一会话的不同调用中会悄然改变。
- **"仅追加 trace"被截断和运行结束时的持久化所破坏。** 如果 trace 在达到 8k/4k 字符限制时丢弃事件，并在崩溃时完全消失，你无法从中重放或审计因果链。
- **工具库没有版本固定。** 针对已更改的 `tools/` 目录重放 session trace 是非确定性的。trace 记录的是 agent *说* 它会做什么，而非实际运行的代码。
- **`emit!` 模糊了效果和值的边界。** 将计划日志、工具结果和 UI 事件混入一个无类型的汇聚点，恰好抹去了函数式编程纪律应当强制执行的效果/值边界。

---

## 6. 可扩展性与增长假设

- **在 8k/4k 处截断保证了重要早期上下文的丢失。** 随着会话增长，规划质量下降。没有任何机制来确定*哪些*先前事件重要——设计只是丢弃最旧的事件。
- **随着库的增长，`tool-index.edn` 会变得过时和嘈杂。** 命名冲突、能力重叠和工具漂移会以设计无法检测或纠正的方式降低 LLM 的选择质量。
- **每个任务一个 `bb -f` 子进程，排除了细粒度超时、协作取消或并行性。** 任何工具调用都没有配额或资源限制。
- **设计没有长时间运行或后台任务的模型。** 每个工具都被假定为同步完成、返回 stdout 并退出。任何现实的 agent 使用场景——监控构建、轮询 API、流式传输结果——在架构上均未得到处理。

---

## 7. 规范与现实之间的差距

- **`:compose` 需要可靠的跨任务数据流**，但 `*result*` 的作用域限于子进程，无法在 `bb -f` 中存活。实践中的组合退化为文件系统传递——而设计从未对此进行规范。
- **"命令行上的 EDN 参数"将间歇性失败**，当嵌套 map 包含带引号、换行符或二进制内容的字符串时。设计将其视为已解决的问题。
- **"在会话结束时持久化 trace"与仅追加的持久性相矛盾。** 最后一个事件和写入调用之间的崩溃会使"唯一事实来源"完全消失。
- **"人类可编辑的 `bb.edn`"** 与每次 `plan-amend!` 时自动重写它的规划器不兼容。经过两次重新规划后，`bb.edn` 对人类和 agent 都将不再连贯。
- **通过 `git commit` 进行工具提升在时间上与执行解耦。** 规划之后的提交会悄然改变运行时行为；trace 从未记录实际使用的工具版本（提交 SHA）。

---

## 8. 竞争现实检验

- **没有类型化的工具接口或 schema 验证的参数。** 严肃的替代方案将 JSON Schema 验证的函数调用视为基本要求。该设计重新发明了一个契约更宽松的劣质版本。
- **没有沙箱、能力作用域、超时或资源限制。** 成熟的系统提供子进程隔离、seccomp、容器或显式能力过滤器。该设计一概没有。
- **没有工具版本控制或测试门控。** 工件版本控制、CI 检查和废弃策略是可重现 agent 系统的标准配置。`git commit` 无法替代它们。
- **没有结构化的可观测性。** 竞争对手跟踪结构化事件、span 和错误分类。`emit!` 加上截断的 EDN 无法替代真正的 agent 可观测性。
- **没有并发或并行任务执行。** 任何涉及独立子任务的 agent 使用场景，在不重新设计核心循环的情况下，在架构上是不可能实现的。

---

## 证伪测试

以下 7 个场景最有可能立即使系统崩溃。它们应该是在可工作的 v1 存在后首先尝试的事情：

| 测试 | 暴露的问题 |
|---|---|
| 生成包含 `s/def` 加破坏性 I/O 的工具 | "验证"通过；不安全代码无阻运行 |
| 强制规划器发出格式错误的 EDN | 循环停滞；没有确定性的恢复路径 |
| 创建包含无限循环的工具 | 没有超时；进程无限挂起 |
| 在计划引用已提升工具后修改该工具 | 会话悄然失去可重现性 |
| 在执行中途杀死进程 | trace 不持久化任何内容；完整审计跟踪消失 |
| 会话增长超过 8k/4k 截断限制 | LLM 丢失关键先前状态；决策质量无警告地下降 |
| 将大型/嵌套 EDN 作为 CLI 参数传递 | 引号/大小失败；任务悄然丢弃或损坏参数 |

## 其他设计层面的关注点

### 来自先前头脑风暴评审

**`*result*` 动态变量：**
动态绑定是线程局部的，在任何情况下都不会跨越 `bb -f` 子进程边界。当前设计承认了这一点，但留下了未解决的缺口。通过动态变量进行任务间数据流，对于主执行路径在架构上是有缺陷的。

**每次调用产生一个进程：**
50ms × N 个任务对于粗粒度计划来说是噪声，但会惩罚链接许多小工具的工作负载——文件 stat/grep/format 循环、紧密的重试序列、多步重构。没有架构变更就没有优化路径。

**`plan-amend!` 作为第一线故障恢复：**
LLM 重新规划不应该是第一个恢复步骤。任务失败几乎总是错误参数、工具错误或环境问题——所有这些在升级到完整重新规划之前，都更适合通过受约束的带反馈重试循环来处理。在第一个错误上跳转到 `plan-amend!` 会浪费完整的 LLM 往返，并且通常会以不同的工具名称重新生成相同的计划。

**工具库作为无界自由形式代码：**
最大的长期风险：使用自由形式生成的代码作为主要行动空间，而没有稳定的、有版本的能力边界。随着库的增长，工具将漂移、重叠和冲突。LLM 会在不同会话中生成同一工具的微妙不同版本。重构核心工具会悄然破坏所有调用它的内容。没有共享契约，没有稳定性层级，没有超越"调用这个函数"的组合原语。

**Session trace 增长：**
当工具嵌入大型载荷（stdout、diff、文件 blob）且长时间运行积累到数十 MB 时，仅追加模型就会崩溃。LLM 看到的是截断的切片，但内存、I/O 和事后分析都会受到影响。没有指定任何压缩、载荷溢出或滚动窗口策略。
